# Production end-to-end test checklist

**Status: Automated renderer and structural regression coverage is active.** The core production workflow has previously passed end-to-end testing. Use this checklist for release verification and for the first live use of materially changed report templates.

Production: `https://report.creation.proinspect.systems/`

## Authentication

- Open the application in a private/incognito browser session.
- Confirm Cloudflare Access prompts for authentication.
- Sign in using an approved `@remotebusinesspartner.com.au` address.
- Confirm the Properties screen loads without an Access or server error.

## Property and report persistence

- Create a temporary test property.
- Refresh the browser and confirm the property remains.
- Sign in from a second browser/device and confirm the property appears.
- Create a draft report, enter representative data, wait for the cloud-save indicator, refresh, and confirm the data remains.
- Do not edit the same draft simultaneously on two devices. If a stale browser attempts to save after another device has changed the draft, confirm the application reports a version conflict rather than silently overwriting the newer cloud version.

## Template and long-content checks

For any new or materially changed template:

- Enter long property/client names.
- Enter commentary long enough to cross at least one A4 page boundary.
- Confirm the issued PDF repeats section/table headers on continuation pages.
- Confirm no text overlaps borders, footers or adjacent columns.
- Confirm long disclaimers and sign-off names wrap or continue cleanly.
- Confirm page numbering is sequential.

The permanent CI regression suite also generates every registered report definition plus long-content stress fixtures.

## Building Manager reports

For Daily and Monthly Building Manager reports:

- Add activities under several operational categories.
- Link each uploaded photo to a specific reporting item.
- Confirm the activity table shows the correct linked-photo count.
- Confirm the PDF photo appendix identifies the category and reporting item.
- Attempt to remove an activity that has linked photos and confirm the UI blocks the deletion.
- Attempt to finalise with an unlinked photo and confirm finalisation is blocked.
- For Monthly reports, confirm the reporting period is present.

## Photo storage and PDF evidence

- Upload representative JPG/PNG/WebP photos from the device.
- Confirm photos are resized/uploaded and display after refresh.
- Assign photos to different areas/categories.
- Set a cover photo.
- Open the report on a second browser/device and confirm photos load from R2.
- Generate a draft PDF and confirm every expected photo is present, correctly oriented and associated with the expected area/item.
- For a photo-heavy report, inspect more than one gallery page.

## Screen preview vs issued PDF

The on-screen report view is a convenient summary preview. The downloaded PDF generated by the deterministic jsPDF renderer is the authoritative issued layout.

- Use **Download Draft PDF** for layout acceptance.
- Do not use the browser preview alone to approve pagination.
- Confirm the PDF opens correctly in at least one mainstream PDF viewer before finalisation when a template has materially changed.

## Finalisation

- Review the validation panel on **Review & Send** and resolve all reported issues.
- Finalise the report.
- Confirm the issued PDF downloads.
- Confirm the report changes to Completed.
- Confirm the completed report can no longer be edited or deleted through the UI.
- Download the stored completed PDF again and compare it with the originally issued PDF.

## Storage checks

- Confirm the report record exists in D1.
- Confirm report photos exist under the expected R2 report prefix.
- Confirm `completed/report.pdf` exists for the completed report.
- Confirm a failed D1 update after an upload does not leave the report pointing to an unavailable R2 object.

## Offline and conflict behaviour

- Temporarily interrupt connectivity while editing a draft.
- Confirm the application reports a cloud-save failure and retains the local cache.
- Restore connectivity and confirm normal cloud saving resumes.
- Where practical, open the same draft in a second browser, save a change there, then try to save from the stale first browser. Confirm the stale save returns a conflict message and does not overwrite the second browser's newer version.

## Cleanup

Delete test drafts that are no longer required. Completed reports are intentionally immutable, so use clearly labelled test data for any finalisation test.
